# ipyfoo

A template for authoring [anywidget](http://anywidget.dev) with Svelte 5, Tailwind 4
and shadcn-svelte.

## Development

Development requires [`uv`](https://github.com/astral-sh/uv) and
[`pnpm`](https://pnpm.io/).

```sh
uv venv
uv pip install -e . --group dev
pnpm dev # start a development server
uv run jupyter lab notebooks/example.ipynb
```

## Renaming the widget

- `py/ipyfoo/` — the package directory
- `pyproject.toml` — `name`, and every `py/ipyfoo` path in the build config
- `vite.config.ts` — `outDir`
- `package.json` — `name`
- `.gitignore` — the ignored static directory
- **`src/App.svelte` and `src/app.css` — the `#ipyfoo-widget` id**, which must match
  in both files

CI is written against the name in `pyproject.toml` rather than a hard-coded one, so
it keeps working after a rename. It will also tell you if you miss something: the
distribution check fails when the wheel does not contain the package and its built
assets, which is the shape a half-finished rename produces — a wheel that installs
cleanly with no frontend in it.

## Continuous integration

`ci.yml` typechecks and lints the frontend, builds the distribution, and installs
that wheel on the oldest and newest supported Python to exercise the API. Keep the
matrix floor in step with `requires-python`: it is what catches syntax a newer
interpreter accepts silently.

`.github/scripts/verify_dist.py` is where the release guards live, and each one
corresponds to a failure this template actually produced:

- The wheel must contain the package. The sdist flattens `py/ipyfoo/` to `ipyfoo/`
  and the wheel is built from the unpacked sdist, so wrong paths give a wheel that
  installs cleanly and contains nothing.
- `main.js` must not carry a sourcemap, or be implausibly large. `pnpm dev` and
  `pnpm build` share an output directory, and a stale dev bundle is invisible until
  someone loads the widget.
- `main.css` must not contain base64, which is how a bundled webfont adds a few
  hundred KB to every widget on the page.

## Releasing

Publishing runs on a `v*` tag, through PyPI's Trusted Publishing, so there is no
API token to store. Before the first release, on PyPI add a pending publisher for
the project naming this repository, the workflow file `release.yml`, and the
environment `pypi` — then create that environment in the repository settings. A
mismatch in any of the three fails at the OIDC exchange.

```sh
git tag v0.1.0 && git push origin v0.1.0
```

The tag version must match `pyproject.toml`, or the release fails before publishing
rather than putting a version nobody can find on PyPI. PyPI is upload-once: a
version can be superseded but never replaced, which is why the GitHub release is
created after the upload rather than before.

Release notes are generated by GitHub, which builds them from **merged pull
requests**. If you commit straight to `main` they will amount to a compare link. To
write them by hand instead, keep a `CHANGELOG.md` and pass `--notes-file` to
`gh release create` in place of `--generate-notes`.

## A widget is a guest

The template renders everything inside a single root element carrying an id, and
`app.css` scopes the theme to that id. This matters more than it looks.

A widget's CSS is injected into the host notebook's document, not into a sandbox. A
stock shadcn theme targets `*`, `body` and `html`, which is correct for an app that owns
the page and wrong here: it would restyle the entire notebook and every other widget
rendered beside yours. The same applies to anything you add — keep selectors under the
root id.

Two related habits worth keeping:

- Never put a `<style>` block inside the markup of a Svelte component. Svelte only
  scopes the one at the top level; a `<style>` in the template compiles to a literal DOM
  node whose selectors are global.
- The widget adopts the host's font rather than bundling one. Bundling a webfont inlines
  its subsets as base64 into your stylesheet — that is around 285KB for Inter, typically
  most of the file, downloaded again for every widget on the page.
